# ЛР3. Категория и вид операции

Вариант: **Customer**.

## Что дано

Предметные объекты, внешний API и вспомогательные типы уже подготовлены. В `app/domain/eligibility.py` даны заготовки общего интерфейса и двух исполнителей. Их поведение и основной метод `CustomerService.check()` требуется завершить самостоятельно. Сигнатуры сохранены; новые слои и выбор архитектуры не нужны.

## Задание

### Шаг 1. Реализуйте общий интерфейс и два поведения

Реализуйте абстрактный класс `CustomerEligibilityRule` и наследников `AllowedCategoryRule` и `AllowedOperationRule`.

Множества разрешённых категорий и операций передаются в конструкторы. Если значение не входит в множество, возвращайте отказ `CUSTOMER_CATEGORY_DENIED` или `OPERATION_DENIED` соответственно. Пустое множество запрещает все значения и не считается ошибкой настройки.

Сервис должен вызывать общий метод `check()`, не выбирая алгоритм по типу правила.

### Шаг 2. Соберите путь вызова в `CustomerService.check()`

Получите клиента, вызовите `availability()`, затем правила по порядку. Верните первый отказ; после всех разрешений — `CheckResult(True)`. Не выбирайте алгоритм по конкретному классу исполнителя.

### Шаг 3. Проверьте повторное использование

Разрешение → блокировка и `CUSTOMER_BLOCKED` → активация и новое разрешение. Результат первого вызова не меняется.

## Примеры и границы

- При категориях `{STANDARD, PREMIUM}` значение `STANDARD` разрешено, `BUSINESS` — нет.
- При операциях `{PURCHASE}` покупка разрешена, `CASH_WITHDRAWAL` — нет.
- Если отказали оба правила, возвращается первый отказ в порядке их передачи.
- Заблокированный клиент получает `CUSTOMER_BLOCKED` до дополнительных проверок.

Последовательности и конфигурации дополнительно проверяются в `tests/test_progression.py`. Прочитайте ожидаемый результат каждого сценария до реализации.

Все проверки открыты: `tests/test_contract.py` и `tests/test_review_contract.py`.
Описание объектов — в [REFERENCE.md](REFERENCE.md), исходные результаты тестов — в [STARTER-STATE.md](STARTER-STATE.md).
